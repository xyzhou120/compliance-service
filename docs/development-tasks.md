# 开发待办与交付顺序

版本：2026-10-25（依据《冲击地压跨文档合规检查服务开发交接与验收方案》）

本文把交接方案中的 M0–M6 转成可执行待办。`pass`、`no_pass`、`pending`、`unverifiable`、`failed` 是业务结果；`completed` 只表示执行流程结束，不能替代业务核验。

## 工作约束

- 继续使用 `compliance-service` 现有账本、租约、输入快照、证据引用和 outbox；不另建第二条结果投递链。
- 清单存在不等于行为已实施；本次范围无记录不等于明确未安排。模型/OCR 只产生候选，不能直接产生 `no_pass`。
- 矿井、运行、环境、文件版本和证据必须隔离；历史结果不可改写，修订创建新运行。
- 凭据只来自部署环境或密钥管理。不得写入代码、日志、快照、测试或文档。
- 每项待办都要留下可重放输入、源码/规则版本、原始文件字节哈希和定位证据。

## T01 统一规则语义与规则版本

目标：消除 `daily_*` 绕过规则前件的判定入口，登记不可变规则 revision。

实施项：

- 统一预警/动力线索、阈值、适用设计、研判、动作时序和结束条件的命题链。
- `candidate`、否定句、泛化等级、`evidence_not_found`、缺日期/工作面、冲突版本不能直接形成 `no_pass`。
- 明确 `explicit_not_arranged` 与 `evidence_not_found`，边界值按规则比较方向处理。
- 旧 revision 保留；规则源变更必须登记新版本和 SHA256，不能复用旧版本名。

交付/证据：规则决策表、三个反例回归测试、规则源哈希及变更说明。

## T02 上游任务接入与控制状态

目标：在基础表配置的 `check_url` 路由受理上游原始报文。

实施项：

- 保存原文、任务/执行标识（如有）、`mineId`、状态、周期、检查项、`resultCallbackUrl` 快照。
- 保持每个检查项独立运行和独立回调；重复 running 具备可解释幂等语义。
- 明确暂停/恢复字符串和执行定位；采用协作式检查点暂停，不伪造“已支持”状态。
- 区分上游调用本服务的 `check_url` 与本服务回调的 URL。

联调前必须确认：正式 itemCode、执行标识、status 枚举、终态后重发、暂停/恢复语义、认证方式。

## T03 OceanBase 只读取证与附件冻结

目标：按服务端资料目录查询 `mineId + checkCycle + items`，冻结查询和附件字节版本。

实施项：

- 只读 repository、参数化 SQL、租户兼容模式显式配置；客户端不能传任意 `file_name_id` 或 URL。
- 建立两项检查的 `itemCode -> file_name_id -> material_group/role/cadence` 白名单。
- 保存查询参数、版本、时间、原始行；按 `attachment_id` 去重，同名不同 ID 保留，内容哈希不同标记冲突。
- 流式下载、HTTPS/重定向约束、PDF 魔数、SHA256、附件身份核对；失败类型单独记录。
- 月内日报和原始记录与年度设计/阈值分开处理，保留登记日期、业务日期、事件时间和有效期。

联调前必须确认：实际 DDL、行更新时间、作废/替换关系、OB 驱动及只读权限、跨月/周验收适用范围。

## T04 文档事实层与候选质量门

目标：保留 PDF/DOCX/XLSX 原文和逐条定位，可靠区分候选、事实、缺口、不可读。

实施项：

- 输入快照含文件、字节哈希、页/行/单元格、文字层、表格和图片覆盖状态。
- 日报线索包含日期、工作面/巷道、事件类型、事件标识、指标/单位/方法、certainty、证据引用和原文。
- 同页多工作面/日期分段；OCR/VLM 按字段交叉核对，失败页可单独重试并可重放。
- 缓存身份包含模型、提示、预算、质量门和解析版本；临时 provider 失败不能固化成最终不可读。

## T05 两项事件核验与连续周期

目标：用同矿、同日期、同工作面和明确事件标识建立可解释事件链。

实施项：

- 停工撤人与卸压：触发确认 → 停工/断电/撤人/报告 → 研判 → 卸压/验收 → 采掘反证。
- 解危效果检验：解危施工 → 原始测值/测点/单位 → 阈值比较 → 技术负责人确认 → 调度解除 → 实际复工。
- 安排、下令、实施、完成、验收分别保存；日期粒度不推断具体先后。
- 相邻日期只有显式连续事件标识才归并；解除后再次预警、新版本和作废关系单独处理。
- 缺证、冲突、未关联和 OCR 不可读进入 `pending`/`unverifiable`，不改写为明确反证。

## T06 回调闭环

目标：每项每次执行生成一条稳定 DTO，通过持久 outbox 投递并确认业务成功。

实施项：

- 映射 `mineId/itemCode/checkCycle/checkTime/checkResult/description/detail/attachments`；周期原样回传，附件周期单独保存。
- 五类结果都带非空 `description`、`detail`；无具体问题时省略 `attachmentContent`。
- 保存 URL 快照、定版时间、同一 payload 和幂等标识；HTTP 与业务响应均成功才算 delivered。
- 超时/5xx 复用同 payload 退避重试；鉴权、报文和业务失败进入可见失败，不重新执行检查。
- 进度至少覆盖 task/run/item、查询/下载/解析/模型/回调耗时。

联调前必须确认：正式回调域名、认证、业务成功判据、幂等字段/请求头和超时约定。

## T07 真实 gold 与 M6 盲测

目标：证明业务准确性和证据定位，而不是证明流程能收束。

实施项：

- 建立真实矿井 gold，专家双标、第三人仲裁；开发集与盲测集隔离。
- 分层统计字段/事件召回、问题精确率、误报/漏报、证据定位率、不可读率、版本冲突和 episode 归并准确率。
- 覆盖阈值小于/等于/大于、不同单位/方法、只有图例、仅计划、明确否定/查无记录、同日独立事件、同字节重复、相反版本、下载/OCR/回调失败与恢复。
- 业务方与独立专家确定指标分母和放行阈值；不在开发文档臆定准确率。

## 当前实施顺序

1. T01 规则语义和不可变 revision。
2. T02/T03 任务适配器、白名单 repository、查询/附件快照。
3. T04/T05 事实质量门和事件核验。
4. T06 DTO、真实 HTTP 回调和 outbox 业务确认。
5. T07 gold、盲测和正式上游联调。

真实 OceanBase、正式上游、真实回调和 M6 专家盲测需要外部环境/人员确认；本地 mock、合成样本和静态检查不能替代这些证据。
